# Basis data autentikasi multimethod

## Kontrak model untuk layanan (ditetapkan sebelum implementasi)

- `User`: `email String? @unique`, `phone String? @unique` (E.164), `phoneVerifiedAt DateTime?`, `smsOtpEnabled Boolean @default(false)` permanen; `emailVerifiedAt` tetap. CHECK `User_sms_otp_verified_check` mengharuskan nomor dan phoneVerifiedAt terisi ketika flag true. `UserRole` menambah `CLIENT`, `VENDOR`; `CUSTOMER` tetap legacy, default akun baru `CLIENT`. Semua relasi bisnis tetap.
- `AuthCredential`: tetap `userId` PK/FK dan `passwordHash`, satu password internal per akun, dapat dipakai login melalui email atau telepon; status verified wajib untuk recovery/link.
- `AuthAccount`: `id`, `userId`, `provider`, `providerAccountId`, `email String?`, `emailVerified Boolean @default(false)`, `createdAt`, `updatedAt`; unique gabungan `(provider, providerAccountId)`, unique `(userId, provider)`. Google memakai provider `google` dan subject terverifikasi sebagai providerAccountId. Metadata email Google bukan izin merge/link otomatis.
- `AuthVerificationToken`: `id`, `tokenHash String @unique`, `purpose String`, `userId String?` FK, `identifier String?`, `payload Json?`, `expiresAt`, `consumedAt DateTime?`, `attempts Int @default(0)`, `createdAt`. Purpose kontrak: `EMAIL_VERIFY`, `PHONE_OTP`, `PASSWORD_RESET`, `ACCOUNT_LINK`, `OAUTH_STATE`. Identifier email/telepon ternormalisasi atau identifier opaque untuk state; payload opsional hanya metadata aman atau envelope terenkripsi PKCE/nonce, tidak berisi token provider/plaintext OTP/password; token hanya hash/HMAC. `userId` nullable untuk pendaftaran/state sebelum akun dibuat. Purpose divalidasi layanan, bukan enum agar kontrak tetap sederhana.
- `UserSession`: kolom existing tetap; tambahan nullable `reauthenticatedAt`, `lastSeenAt`, `revokedAt`, `userAgent String? @db.VarChar(512)`, `ipHash String?`. Session revoked atau expired wajib ditolak server. Jangan menyimpan IP mentah atau token di metadata.
- `AuthLoginThrottle`: tetap tanpa perubahan kontrak.

## Batas akses layanan

Registrasi runtime harus mengabaikan input role/status; gunakan default Prisma CLIENT/ACTIVE. Prisma 7 mengirim nilai default pada INSERT: grant INSERT role/status disertai trigger `auth_guard_runtime_registration` yang menolak selain CLIENT/ACTIVE untuk `menujuakad_runtime_preproduction`. Runtime hanya mendapat INSERT kolom registrasi dan UPDATE kolom identitas yang diperlukan, tidak UPDATE role/status, tidak DELETE User. Provisioning VENDOR/SUPERADMIN dikerjakan melalui jalur administratif terpisah dengan kredensial owner, bukan form publik.

Link/unlink/reset wajib transaction: lock row User (`SELECT ... FOR UPDATE`) terlebih dahulu, lalu token/account, periksa sesi/reauthentication, identitas terverifikasi, dan metode login yang tersisa. Signup/reservasi identitas yang belum mempunyai row dapat memakai advisory transaction lock atas identifier terkanonisasi; constraint unique tetap menjadi pertahanan final. Jangan merge akun berdasarkan email Google.

Token dikonsumsi dengan conditional UPDATE `consumedAt IS NULL AND expiresAt > now()` plus purpose/user/identifier sesuai konteks; hanya tepat satu row terdampak boleh melanjutkan. Perubahan password, konsumsi token, revoke semua sesi, dan pembuatan sesi pengganti harus atomik. Unlink wajib memastikan minimal satu metode login terverifikasi tetap ada di transaction yang mengunci user. OTP memerlukan attempts atomik dan pembatasan pengiriman di layanan. Google OAuth state harus terikat cookie/browser dan tujuan login/link.

## Strategi migrasi dan preflight

1. `20261009000000_auth_roles`: hanya menambah CLIENT/VENDOR pada enum. Migrasi terpisah karena PostgreSQL tidak boleh memakai nilai enum baru sebelum transaction penambahannya committed. CUSTOMER/SUPERADMIN existing tetap.
2. `20261009001000_auth_multimethod`: transaction eksplisit, lock User `SHARE ROW EXCLUSIVE`, lock timeout5 detik dan statement timeout60 detik; audit konflik dilakukan sebelum perubahan data atau DDL lain. Pemeriksaan ulang di bawah lock melindungi dari perubahan sejak preflight awal.
3. Email dipangkas/lowercase; phone membuang pemisah format aman, menerima nomor `+…`, mengubah awalan Indonesia `0…` ke `+62…` dan `62…` ke `+62…`. Angka lokal negara lain tanpa kode internasional ditolak. Angka yang tidak memenuhi E.164, phone kosong/nonangka, email kosong, collision setelah normalisasi menyebabkan `AUTH_PREFLIGHT_CONFLICT` dan rollback penuh. Tidak ada merge atau penghapusan akun. Format email RFC penuh tetap divalidasi layanan; migrasi hanya memeriksa kosong/collision canonical.
4. Setelah semua hitungan nol: normalisasi, email nullable, default CLIENT, phoneVerifiedAt + unique/check, metadata sesi, account/token serta CHECK baru. Hash credential/session/throttle dan identitas User tidak diganti.
5. Trigger `User_runtime_registration_guard` membatasi INSERT dari role runtime bernama `menujuakad_runtime_preproduction` menjadi CLIENT/ACTIVE. Owner tetap dapat seed/provision legacy CUSTOMER atau admin. Runtime tidak mendapat UPDATE role/status. Bila nama role runtime diubah, guard dan grants harus disesuaikan melalui migrasi terencana.

6. `20261009002000_auth_sms_policy`: transaction lokal dengan lock timeout5 detik/statement timeout60 detik; ADD COLUMN BOOLEAN NOT NULL DEFAULT false dan CHECK `User_sms_otp_verified_check`. Tidak mengubah contact, timestamp verifikasi, credential, sesi atau relasi bisnis; akun verified existing juga tetap false. Tidak menambahkan indeks boolean karena flag dibaca bersama User berdasarkan PK/login identifier, bukan filter seluruh akun.

`auth-multimethod-preflight.sql` adalah SELECT read-only dengan empat hitungan konflik; tidak mencetak nilai email/telepon, token atau ID akun. Konflik harus diselesaikan dengan bukti kepemilikan oleh operator. Jika akun lama belum punya bukti contact, jangan otomatis mengisi emailVerifiedAt/phoneVerifiedAt.

Pipeline identitas: input → validasi/canonicalisasi layanan → transaksi reservasi + constraint unique → User/credential/account → challenge proof hash → konsumsi atomik → badge verified/sesi. Pipeline migrasi: snapshot/backup → preflight hitungan → penyelesaian konflik manual → migrasi enum committed → migrasi schema transaction → pemeriksaan metadata → grants least privilege → smoke auth.

## Concurrency dan invariant layanan

Urutan lock disarankan selalu User lalu token/account; ketika dua identifier diperlukan, lock identifier dalam urutan leksikografis untuk mengurangi deadlock. Signup/reservasi identifier yang belum mempunyai row membutuhkan `pg_advisory_xact_lock` dengan namespace canonical identifier atau isolasi serializable dengan retry bounded. Unique constraints tetap harus diterjemahkan menjadi konflik generik; jangan mengandalkan SELECT sebelum INSERT.

Reset/link proof membutuhkan conditional UPDATE dan pemeriksaan jumlah row; token expired/consumed/purpose lain tidak boleh diterima. Konsumsi proof dan perubahan identitas/password/sesi wajib dalam transaction yang sama. Link Google tidak mengubah pemilik subject existing. Unlink dua metode paralel harus lock User yang sama, mengecek ulang metode tersisa di transaction, dan menolak pelepasan metode login terakhir. Enable SMS OTP memerlukan AuthCredential existing, provider SMS ready, phone terverifikasi dan reauth terbaru; CHECK hanya menjaga invariant satu row User, keberadaan credential lintas tabel tetap diperiksa layanan di bawah lock. Unlink nomor atau pembatalan verifikasi harus sekaligus mengubah smsOtpEnabled=false bersama phone/phoneVerifiedAt dalam satu UPDATE atomik; pemisahan UPDATE ditolak CHECK ketika flag masih true. Tidak ada fallback yang melewati faktor SMS enabled ketika provider tidak siap.

Attempts OTP harus bertambah atomik meski jawaban salah; jangan melempar error dari transaction setelah increment bila error tersebut menyebabkan rollback hitungan. Commit hasil kegagalan proof lalu berikan respons aman. Recovery mengacu pada contact verified saat ini; jika contact berubah, invalidate proof lama dan cocokkan identifier terhadap row User terbaru di bawah lock. RevokedAt/expiry/session ownership dan waktu reauthentication harus diperiksa pada setiap operasi sensitif.

## Least privilege dan penerapan manual

`auth-runtime-grants.sql` kini memberi:

- User: SELECT; INSERT kolom registrasi termasuk default role/status yang dibatasi trigger; INSERT/UPDATE kolom smsOtpEnabled diperbolehkan; UPDATE hanya identitas/profile/verification/smsOtpEnabled/lastLoginAt/updatedAt, tanpa role/status/id/createdAt; tanpa DELETE.
- Credential: SELECT/INSERT/DELETE, UPDATE passwordHash saja; userId immutable untuk runtime.
- Session: SELECT/INSERT/DELETE, UPDATE reauthenticatedAt/lastSeenAt/revokedAt/userAgent/ipHash saja; userId/tokenHash/expiry immutable.
- Account: SELECT/INSERT/DELETE, UPDATE email/emailVerified/updatedAt saja; subject/provider/userId immutable.
- Verification token: SELECT/INSERT/DELETE, UPDATE consumedAt/attempts saja; hash/purpose/identifier/userId/payload/expiry immutable.
- Throttle, draft invitation/couple/section, PaymentTestRequest: hak existing dipertahankan. Tidak menambah DDL, ALTER role, akses provider komersial atau bypass ownership server.

Skrip mencabut grant table/kolom yang dapat melemahkan batas immutable; seluruh penerapan transaction. Skrip menolak role super/createdb/createrole/replication/bypassrls, role dengan membership/inheritance, ownership schema/object atau CREATE public. Inspection sebelum eksekusi tetap diperlukan; grant DML ini bukan pengganti pemeriksaan izin/ownership di server.

Runtime Neon existing dilaporkan baca terbatas oleh progres proyek; **grant baru belum diterapkan**. DevOps/owner harus mengambil snapshot dan memastikan pemulihan, membaca `auth-runtime-inspect.sql`, menjalankan preflight read-only, menerapkan migrasi terencana pada database pengembangan lalu target aktif, dan baru menjalankan `auth-runtime-grants.sql`. Gunakan credential owner untuk tooling, jangan mengganti DATABASE_URL runtime menjadi owner. `auth-preproduction-inspect.ts --multimethod` menambahkan pemeriksaan15 tabel, seluruh6 migrasi (termasuk auth_sms_policy) dan12 CHECK (termasuk User_sms_otp_verified_check); mode default historis13 tabel tetap tersedia. Kontrak daftar migrasi/CHECK inspeksi diverifikasi terhadap metadata PGlite lokal; command inspeksi tidak dijalankan ke Neon aktif. Jangan menjalankan migrasi atau seeder langsung dari runtime aplikasi.

Rollback utama adalah transaction migrasi kedua sebelum commit. Migrasi enum pertama dapat tetap tercatat setelah migrasi kedua gagal; itu aman dan tidak memerlukan menghapus enum. Setelah conflict diperbaiki, operator perlu memeriksa status migrasi gagal dan menggunakan prosedur Prisma resolve yang tepat sebelum retry. Sesudah data phone-only/token/account nyata dibuat, down migration dengan mengembalikan email NOT NULL atau menghapus tabel tidak aman; gunakan forward fix atau restore snapshot terencana. App lama tidak boleh menerima akun phone-only sampai kompatibilitas email nullable terverifikasi.

## Privasi, retensi dan keterbatasan

Email, phone, provider subject/metadata email, token.identifier, avatar dan userAgent merupakan data pribadi. Gunakan akses server-only, TLS/provider encryption at rest, backup terlindungi, log agregat, dan DTO profil/sesi yang hanya mengungkap data akun sendiri. OTP berentropi rendah harus HMAC dengan secret dan purpose/identifier/context; hash tanpa secret tidak cukup untuk menahan brute force database. OAuth payload yang memuat PKCE/nonce sensitif harus envelope terenkripsi dan terikat browser; schema tidak melakukan enkripsi sendiri. Tidak ada kolom password, code OTP atau bearer token plaintext.

Saran operasional: token/state kedaluwarsa dan consumed proof dibersihkan setelah jendela diagnosis singkat (misalnya24 jam); sesi expired/revoked setelah retensi audit terbatas (misalnya30 hari); metadata userAgent/IP hash hanya bila dibutuhkan daftar sesi/risiko. Kebijakan final dan job cleanup belum diimplementasikan pada tugas schema ini. DELETE token/session telah disediakan untuk job yang sah, tanpa timer background di route.

PGlite memakai PostgreSQL WASM lokal dengan satu koneksi terkelola. Uji Promise.all pada konsumsi token membuktikan conditional UPDATE hanya mengonsumsi sekali untuk permintaan berurutan yang berebut, bukan bukti contention dua koneksi Neon/PostgreSQL independen. Pengujian multi-connection advisory/row locks, delivery Google/email/SMS, kemampuan runtime aktual dan produksi masih perlu diverifikasi terpisah. Skema saja tidak membuktikan autentikasi backend selesai.
